# 校园时间银行 · 测试用例

> 最后更新：2026-06 | 适用版本：v1.0.0

本文档是**可操作的功能测试用例集**，按 10 个模块组织，共 **56 条**用例。
每条都写明了前置条件、操作步骤、预期结果，并留有「实际结果 / 通过」两列供执行时填写。

**执行前提**：需要有**两个微信号**（记为 **账号 A**、**账号 B**）和一个**管理员账号**。
测试环境建议用云开发**测试环境**而非生产环境，避免污染数据。

**生成测试数据的快捷方式**：调 `initdb` 云函数的 `{"action":"init"}` 写入演示数据
（7 个用户 / 8 个技能 / 6 张不同状态的订单），这会让大部分列表页都有数据可看。
`{"action":"clear"}` 可恢复初始状态（会保留管理员账号与基础配置）。

## 二、边界与异常测试要点

以下是**在功能测试之外必须覆盖的边界条件清单**，按「资金安全 → 状态机 → 权限 → 输入 → 性能」排列。
每一条都对应了本项目里真实存在的守卫代码，测试时可以直接对照实现确认。

### 2.1 资金安全边界（最高优先级）

| # | 边界场景 | 期望行为 | 对应实现 |
|---|---|---|---|
| 1 | **余额恰好等于价格**（10 枚 vs 10 枚） | 下单成功，余额归零，不出现负数 | `canOrderSkill` 用 `coins < price` 判断（等于时放行） |
| 2 | **余额比价格少 1 枚** | 拒绝，且提示里带**精确差额**「还差 1 枚」 | `canOrderSkill` 的 `skill.price - buyer.coins` |
| 3 | **两个请求并发下同一单** | 只成功 1 单，`coins + frozenCoins` 守恒 | 事务写冲突自动重试 + 同一快照校验（`order.create`） |
| 4 | **两个请求并发接同一单** | 只成功 1 次，第 2 次返回 409「该订单已被处理」 | 条件更新 + `res.stats.updated !== 1` 判定（`order.accept`） |
| 5 | **同一订单被「定时任务」和「用户手动确认」同时结算** | 只结算 1 次，卖家不会收到双倍 | 事务内 `assert(txOrder.status === 'confirming')`（`settleOrder`） |
| 6 | **重复执行 `autoTask`** | `closed`/`settled` 计数均为 0，余额/流水/统计不重复变化 | `closeAndRefund` 与 `settleOrder` 内部的状态断言 |
| 7 | **取消订单后 `frozenCoins` 归零** | `frozenCoins` 不会被扣成负数 | `Math.max(0, b.frozenCoins - amount)` 兜底 |
| 8 | **时间币为 0 的用户下单任何技能** | 拒绝，提示「时间币不足，还差 N 枚」 | 同上第 2 条 |
| 9 | **注册赠送只发一次** | 反复登录不重复赠送 | `login` 按 `_openid` 查用户，`isNew` 才发 `bonus` |
| 10 | **平台总量守恒** | 任意操作前后，`Σ(coins + frozenCoins)` 不变（注册赠送/管理员调整除外） | 冻结/解冻/结算都是「转移」而非「增发」 |

| 68 | 订阅消息发送失败 | ★ **不阻断主流程**（`sendSubscribe` 内部 `try/catch`），站内通知照常 |

## 三、自动化测试说明

本项目有**两套自动化测试**，它们是上述人工用例的「快速前置关卡」：
先用它们把可以自动化的部分跑通，人工测试只需关注 UI 交互与真实云环境行为。

### 3.1 第一套：离线数据层冒烟测试

**命令**：`node tools/smoke-test-mock.js`

**它验的是什么？**

`Campus Time Bank/envList.js` 未填 `ENV_ID` 时，整个小程序跑在 `utils/mock.js` 之上。
这个脚本在 **Node 环境**里把 `utils/api.js` 声明的**每一个 action** 都真实调用一遍，
确保**零云环境**下所有页面都有数据可渲染 —— 这是答辩彩排的保险。

**原理**：

1. **自动发现被测对象**：用正则 `call\(\s*'([A-Za-z_]\w*)'\s*,\s*'([A-Za-z_]\w*)'` 从
   `Campus Time Bank/utils/api.js` 的源码里提取全部 `call('namespace', 'action')`，
   得到 **63 个** `[命名空间, action]` 组合。**新增 action 会自动被纳入**，不用改测试脚本。
2. **构造真实参数**：从 `mock.store`（`utils/mock.js` 导出的内存数据）里动态查找
   真实存在的 id —— 一个「不是我自己发布的、上架中的」技能用于下单，
   一个「我发布的、没有进行中订单的」技能用于删除，一个会话用于聊天等。
   **不写死 id**，所以 mock 数据调整后测试不会假失败。
3. **两阶段执行**：
   - **阶段 1**（约 53 个 action）：跳过依赖订单的业务，逐个调用并断言无异常。
     某些 action 有副作用（如 `submitCampusAuth` 会把状态改成「审核中」），
     用 `AFTER` 表做状态修正，避免污染后续用例。
   - **阶段 2**（10 个 action）：先合成订单，把订单状态机的**每条迁移真的跑一遍**并做**硬断言**。
4. **退出码**：`0` = 全部通过，`1` = 有失败（可直接接 CI）。

**阶段 2 的硬断言（这是最有价值的部分）**：

| 断言 | 内容 |
|---|---|
| ① 卖家流程 | `waiting → ongoing → confirming` 迁移正确，`finishTime` 被写入 |
| ② 拒单退款 | `reject` 后状态为 `closed`，且**买家 `coins` 精确增加 `amount`**（比对退款前后） |
| ③ 取消不扣分 | `waiting` 阶段 `cancel` 后，买家信用分**完全不变** |
| ④ 结算到账 | `confirm` 后状态为 `finished`，**卖家 `coins` +1**、**信用分 +2** |
| ⑤ 评价写入 | `reviewCreate` 后 `orders.isRatedBuyer` 变为 `true` |
| ⑥ 消息落库 | `message.send` 后 `messages` 里该会话的消息数**精确 +1** |

**当前结果**：

```
离线数据层冒烟测试 —— 共 65 个 action

通过 65   失败 0   跳过 0

覆盖率：65/65 个 action 在离线模式下可用
```

**它不能验什么（边界要说清）**：它测的是 `utils/mock.js` 这个**前端模拟数据层**，
不涉及真实的云函数、数据库、事务。所以它能回答「离线预览时每个页面都有数据吗」，
不能回答「真实环境下的并发和权限对不对」。

### 3.2 第二套：云函数离线回归测试（★ 更有说服力）

**命令**：

```bash
node tools/test-cloudfunctions/run.js              # 跑全部案例
node tools/test-cloudfunctions/run.js order        # 只跑文件名含 order 的案例
node tools/test-cloudfunctions/run.js wallet       # 只跑 wallet 案例
TB_TEST_VERBOSE=1 node tools/test-cloudfunctions/run.js   # 打印云函数原始 console 日志
```

**它验的是什么？**

用一套**纯 Node、零依赖、不连云环境**的测试，把 `order`（时间币事务核心）
和 `wallet`（钱包统计）的**全部业务规则**跑一遍。这是本项目**技术含量最高的测试资产**，
因为时间币的冻结/结算/退款/超时逻辑一旦写错就是资金错误，必须有自动化保护。

**规模**：**88 组 / 1901 条断言 / 121 次数据库事务（其中 7 次写冲突自动重试）**，约 1 秒跑完。

**目录结构**：

```
tools/test-cloudfunctions/
├── run.js                      入口：加载案例 → 打印分组报告 → 设置退出码
├── README.md                   测试说明（含「暂时没有覆盖的部分」）
├── stub/wx-server-sdk.js       ★ 内存版 wx-server-sdk（含事务的隔离/冲突检测/重试语义）
├── lib/harness.js              模块解析劫持 + 断言引擎 + 报告渲染
├── lib/fixtures.js             夹具：用户 / 技能 / 配置 / 订单 + 调用云函数的便捷方法
└── cases/
    ├── order.create.test.js    组 1-4   下单冻结 / 校验错误码 / ★并发防超卖 / 信用等级上限
    ├── order.flow.test.js      组 5-8   accept 并发抢占 / reject·cancel / ★finish→confirm 结算 / list·detail·counts
    ├── order.timeout.test.js   组 9-10  超时兜底（惰性 + autoTask）/ 幂等 / 单批上限
    └── wallet.test.js          组 11-13 wallet.info / logs / stats
```

**原理（两个关键设计）**：

**① 测试直接跑仓库里的真源码，不存副本。**
`lib/harness.js` 在加载被测模块**之前**劫持 `Module._resolveFilename`：

| 源码里的写法 | 实际被解析到 |
|---|---|
| `require('./shared')`（来自 `cloudfunctions/<fn>/index.js`） | `cloudfunctions/_shared/index.js`（唯一事实来源） |
| `require('wx-server-sdk')`（任何文件） | `tools/test-cloudfunctions/stub/wx-server-sdk.js` |

因此测试跑的永远是仓库里那一份实现：**实现一改，测试立刻跟着变**，
不存在「测试副本与实现脱节」。`run.js` 的「组 0」还会显式断言
`_shared/index.js` 已加载、而 `order/shared`、`wallet/shared` 这两个由
`tools/sync-shared.mjs` 生成的副本**没有被加载**。

> 注意：部署前仍必须执行 `node tools/sync-shared.mjs` —— 测试绕过副本是为了测试，不是为了部署。

**② 伪造的 SDK 提供了「像真数据库」的事务。**
`stub/wx-server-sdk.js` 实现了云函数真正用到的那一小块能力：集合查询
（`where/orderBy/field/skip/limit/get/count/update`）、文档操作
（`doc().get()/update()/set()`）、指令（`_.in/_.lt/_.and/_.or/_.push/_.inc` …），
以及最关键的 `runTransaction()`：

1. **快照隔离**：事务开始时对全库做快照，事务内所有读写都发生在快照上；
2. **提交时写冲突检测**：若本事务执行期间有别的请求提交过 → 判定冲突，**整个事务重跑**（最多 8 次）；
3. **按文档提交**：提交时只把「本事务真正写过的文档」合并回主库，所以事务之外并发写入的
   时间币流水、站内通知不会被覆盖 —— 这正是真实数据库的行为。

> 第 2 条是「并发防超卖」测试有意义的前提：如果没有冲突检测，4 个并发下单会各自读到同一份
> 余额、互相覆盖，测试就变成了自欺欺人。报告里那句「**其中写冲突自动重试 6 次**」
> 就是这套机制真的被触发过的证据。

**答辩里可以直接引用的三组证据**：

| 组 | 断言要点 |
|---|---|
| **组 3 · ★ 并发防超卖** | 4 个并发下单**只成功 3 单**；`coins + frozenCoins` 恒为 10；订单金额之和 = 买家冻结额；技能 `orderCount` 不丢计数；**事务冲突重试次数 > 0** |
| **组 7 · ★ finish → confirm** | 确认前「钱锁在买家名下、卖家余额为 0」；确认后冻结清零、卖家到账、双方 `+2`；`totalEarned/totalSpent` 与 `serveCount/buyCount` 同步累加；**`coins + frozen` 总量守恒**；连续 5 单额外 `+3`；徽章去重补发 |
| **组 10 · autoTask 幂等** | 定时触发器无登录态可跑；**重复执行 `closed/settled` 均为 0**，余额、流水、`serveCount` 不重复变化；单批上限 50（60 张超时单分两轮处理完） |

**当前结果**：

```
[1/20] 组 0 · 自检：被测模块确实是仓库里的真源码            ✓ 全通过
...
[4/20] 组 3 · ★ 并发防超卖：4 个并发 create 只成功 3 单，coins+frozenCoins 守恒   ✓ 全通过
...
[20/20] 组 13 · wallet.stats：近 7 天趋势 + 支出分类分布      ✓ 全通过

通过 1901 / 失败 0   断言总数 1901
数据库事务 114 次（其中写冲突自动重试 6 次）
```

**★ 它不能验什么（必须主动说明，这是「诚实」而不是「示弱」）**：

测试台自己的 `README.md` 里有一节「暂时没有覆盖的部分」，如实写明：

| 未覆盖项 | 原因 | 影响 |
|---|---|---|
| `geoNear` 地理查询 | 内存 stub 未实现地理索引与 R 树结构 | 「附近技能」只能靠**部署后人工回归**验证 |
| 聚合管道 `$` | stub 只按需实现了云函数真正用到的指令 | `admin.stats` 的部分聚合逻辑不在自动化范围内 |
| `watch` 实时推送 | 这是云开发的长连接能力，无法在进程内模拟 | 实时聊天只能靠**真机双账号**验证（见 TC-08-01） |
| 真实 `openapi.subscribeMessage` 返回码 | 会发起外网调用 | 只断言「是否发起了调用」，不断言返回码 |
| 单次 `get` 的 1000 条上限 | 内存库无此限制 | 大数据量下的分页行为需真实验证 |
| 冷启动、并发压测 | 与运行时环境相关 | 性能结论需在真实环境测 |
| 权限层（集合权限、`requireAdmin` 之外的真实鉴权） | 内存 stub 不做权限校验 | 权限相关用例（§2.3）必须**人工在真环境验证** |

**所以要如实表述**：这套测试覆盖的是**业务规则与资金正确性**（这是最容易出错、最值得自动化的部分），
**不覆盖网络层与权限层**。说清边界比宣称「全覆盖」更经得起追问。
