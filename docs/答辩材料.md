## 一、3 分钟答辩讲稿（约 900 字，可直接念）

尊敬的各位老师，我的毕业设计题目是《校园时间银行 —— 基于微信云开发的大学生技能互助平台》。

### 1. 背景与痛点（约 180 字）

大学生群体里有大量可交换的技能：有人会弹吉他，有人擅长修图，有人高数很好。
但现实中这种互助很难发生，原因有三个：
**第一，找不到人。** 需求发布在班级群里会被瞬间刷掉，信息无法沉淀；
**第二，不好意思谈钱。** 同学之间提供一次帮助，收 50 块钱显得很功利，不收又难以持续；
**第三，没有信任凭证。** 你不知道对方靠不靠谱，也没有机制约束爽约。

### 2. 解决方案（约 170 字）

我做了一个校园技能互助小程序，核心设计是引入一种**平台内部的虚拟计数单位 —— 时间币**。
你帮别人一次，赚到若干时间币；你需要别人帮忙，就花掉时间币。
**1 次服务对应若干时间币，时间币不可充值、不可提现，只能通过帮助他人获得。**
这样就绕开了「同学之间谈钱」的尴尬 —— 你付出的不是钱，是你曾经帮过别人的记录。
同时平台用信用分、徽章、举报与管理员仲裁来建立信任。

### 3. 核心机制（约 220 字）

整套系统最关键的设计是**时间币的冻结—结算双阶段记账**。
下单时并不直接把时间币打给服务方，而是从买家的「可用余额」划入「冻结额」——
**钱仍然属于买家，只是被锁住不能再花**。此时如果服务方拒单、双方取消、或者 24 小时无人接单，
系统就把冻结额原路解冻退回。只有买家确认服务完成后，冻结额才真正扣除并结算给服务方。
**这个设计的关键意义是：任何时刻平台的时间币总量恒等于所有用户「可用余额 + 冻结额」的总和，账实永远对得上。**

成本上，结算这一步涉及四处改写 —— 买家减冻结、卖家加余额、订单置完成、双方统计更新 ——
必须同生共死，所以我用了云开发数据库的**事务**。同时事务内统一采用
**「先把文档读出来、在 JS 里算出绝对值、再写回绝对值」**的写法，**刻意不使用 `_.inc()` 这类更新指令**，
避免更新指令在事务内的语义不确定性导致余额算错。

### 4. 技术亮点（约 200 字）

除了事务，还有三个我认为有技术含量的点：

**一、并发下单不超卖。** 余额校验和扣减在同一个事务、同一份快照里完成。
两个请求同时下单时，后提交的事务会遇到写冲突并自动重试，重试后读到的是对方已经扣减过的新余额，
余额不足就直接回滚 ——「够不够」和「扣没扣」是一个原子判断。

**二、超时处理做了「双保险」。** `order` 云函数配了每 10 分钟的定时触发器批量兜底超时订单；
同时任意用户查看订单数量时，云函数会顺手做一次惰性检查。
定时任务漏跑或延迟时，用户侧的访问就能补上，两条路径共用同一组内部函数且都有状态断言，重复执行是幂等的。

**三、实时聊天零第三方依赖。** 我把 `messages` 集合的权限设为「所有用户可读，仅创建者可写」，
客户端就能用云开发原生的 `db.watch()` 建立长连接实时收消息；
但**写入仍然强制走云函数**，服务端会校验双方确实是会话成员。
连接断开时自动降级为 3 秒轮询，页面销毁时关闭连接防止泄漏。

另外，附近技能用云开发原生的地理位置查询 `geoNear` 实现，结果自带距离字段，
**完全不需要腾讯位置服务这类第三方 SDK 和 Key**。

### 5. 不足与展望（约 130 字）

项目还有明显的不足。**第一**，为了保证 `watch` 实时聊天，`messages` 集合开放了读权限，
理论上其他用户能读到不属于自己的消息，生产环境应该改成服务端推送或长轮询来彻底关闭读权限。
**第二**，信用分规则的权重目前是经验取值，缺少真实数据支撑，未来应做参数敏感性实验。
**第三**，自动化测试用的是内存 stub，**不覆盖真实云开发的网络与权限层** ——
`geoNear` 地理索引、聚合管道、`watch` 推送、订阅消息真实返回码都不在范围内。

后续我计划接入校园统一身份认证、把信用分规则做成可配置的，并引入推荐算法优化技能匹配。

以上就是我的汇报，请各位老师批评指正，谢谢！

## 三、22 个高频答辩问题与参考答案

### Q1. 为什么用时间币，而不是现金或者积分？

**现金的问题**：同学之间提供一次帮助收几十块钱，社交压力大；而且一旦收钱，平台就涉及
资金托管、支付资质、退款纠纷、税务等一整套合规问题，对一个本科毕业设计来说是灾难性的复杂度。

**积分的问题**：传统积分通常是「平台单向发放、只减不增（或能充值获取）」，
它与「你为他人付出的劳动」没有对应关系。如果积分能充值，本质还是钱；
如果只能靠签到领取，那积分会通胀、失去稀缺性。

**时间币的差异**在于**它是双向闭合的**：你只能通过帮助别人来获得，只能通过求助别人来消耗。
总量的增加只有「新用户注册赠送」这一个入口（默认 5 枚），是一个受控的、近似零和的经济体。
这就把「同学互助」从金钱交易变成了**劳动记录的交换**，既保留了对等性，又消除了金钱的尴尬。

（如果老师追问「那时间币是不是代币/虚拟货币」：不是。它没有区块链、不可转让、不可交易、
不可兑换法币，只在平台内作为服务计量的计数单位，本质更接近「图书馆的借阅额度」。）

### Q2. 为什么不需要微信支付资质？

因为**全流程没有任何真实资金流动**，只有数据库字段的加减。

具体来说，所有涉及「钱」的操作都落在两个字段上：`users.coins`（可用余额）和
`users.frozenCoins`（冻结额），由云函数执行 `update`，同时写一条 `wallet_logs` 流水。
整个过程没有商户号、没有 `wx.requestPayment`、没有调用任何 `cloud.openapi.*pay*` 接口。

微信支付资质是针对「小程序内代收代付真实资金」的监管要求。
本平台不存在资金池、不存在充值提现、不存在资金结算，所以不触发这个要求。
在提审时我也会在审核备注里明确写明「使用虚拟时间币，不涉及任何真实资金交易」。

（可以补充：这也是为什么我在代码规范里明确禁止出现「¥ / 元 / 付款」这类支付词汇 ——
不只是文案统一，也是为了让审核员和评委一眼看出这与支付无关。）

### Q3. 时间币怎么防超发？总量怎么控制？

时间币只有三个入口和三个出口，全部在云函数里硬编码，客户端无写权限：

**入口（增加时间币）**：
1. **注册赠送** —— `login.login` 首次调用时按 `config.registerBonus` 发放（默认 5 枚），
   有 `isNew` 判断保证只发一次，且**同一 openid 只会有一条 `users` 文档**；
2. **服务收入** —— 卖家在订单结算时收钱，**这笔钱恰好等于买家支出的金额**，是转移而非增发；
3. **管理员调整** —— `admin.adjustCoins` 用于纠纷仲裁，会写 `admin` 类型的流水留痕，
   是**唯一**能被审计的人为增发路径。

**出口（减少时间币）**：只有买家确认完成后的 `expense` 结算，以及管理员调整。

关键约束是：**服务收入与买家支出是同一笔金额的转移**，所以在订单流转过程中
平台总量不变。真正会增发的只有「注册赠送」和「管理员调整」两项。

**对账方法**：平台流通量 `coinCirculation = Σ users.coins`，
冻结总量 `coinFrozen = Σ users.frozenCoins`，两者之和应等于
「注册赠送累计 + 管理员调整累计」。管理端看板的 `overview` 里直接暴露了
`coinCirculation` / `coinFrozen` / `coinEarned` 三个数字，随时可以核对。

### Q4. 下单为什么用「冻结」而不是直接扣？

这是整个系统最重要的设计决策，有三个理由：

**第一，直接扣款在业务上是错的。** 时间币是「下单即从买家账上消失，打给卖家」的话，
一旦卖家拒单、双方取消、或者 24 小时没人接单，钱已经在别人账上，平台**没有任何强制手段追回**。
只能靠管理员手动改数据，那就不是一套可信的系统。

**第二，冻结让「钱仍然属于买家」这个语义准确。** 从买家的心理模型看，我下单时钱被锁住了，
但还没花出去；如果订单没成，钱还会回来。这与真实世界的「预授权冻结」是一致的。

**第三，冻结让不变量可校验。** 因为任何时刻都有
`平台总量 ≡ Σ(可用余额 + 冻结额)`，一笔下单只是把金额从「可用」搬到「冻结」，
总额不变；一笔结算才真正转移。这个不变量简单到可以用一行 SQL（或一次遍历）验证，
是整个账务系统可证明正确的基础。

### Q5. 并发下单会不会超卖？云开发事务是怎么用的？

**结论：不会超卖。** 机制分两层：

**第一层，事务外快路径预检**（`order/index.js` 的 `actionCreate` ①）：
先读一次技能和买家，用 `canOrderSkill()` 检查「技能上架 / 不能买自己的 / 已认证 /
信用分达标 / 余额充足」。这一层**只是为了让用户尽早看到友好的错误提示**，
因为抛错前还没进事务，成本低。

**第二层，事务内重读重判**（这是真正的判定）：

```js
const r = await db.runTransaction(async tx => {
  const sRes = await tx.collection('skills').doc(skillId).get()
  const bRes = await tx.collection('users').doc(buyer._id).get()
  const txSkill = sRes.data
  const txBuyer = bRes.data
  canOrderSkill(txSkill, txBuyer, config)       // ← 在事务内再判一次
  const coins = (txBuyer.coins || 0) - amount   // ← 用同一份快照算绝对值
  const frozenCoins = (txBuyer.frozenCoins || 0) + amount
  await tx.collection('users').doc(buyer._id).update({ data: { coins, frozenCoins } })
  ...
})
```

如果余额是 10 枚，两个请求各想扣 6 枚：
两个事务都读到「10 枚」，都算出「4 枚」，都想写回 `coins: 4`。
云开发的事务是**乐观并发控制**：先提交的那个成功；后一个提交时检测到
自己读过的文档已经被别人改过（写冲突），会**自动重试**整个事务函数。
重试时读到的是「4 枚」，`canOrderSkill()` 检查 `4 < 6` 抛出 409，
事务回滚 —— 客户端收到「时间币不足，还差 2 枚」的正确提示。

**所以「够不够」和「扣没扣」是在同一份快照上的一个原子判断**，
不存在两边都读到 10 枚、各扣 6 枚的经典超卖场景。

（同构的还有 `order.accept`：它不用事务，而是用**条件更新**
`.where({ _id, status: 'waiting' }).update({...})` 作为「原子抢占」，
通过检查返回的 `res.stats.updated === 1` 来判断自己是否抢到了这单。
两个并发的接单请求只有一个能改到 `status='waiting'` 的文档。）

### Q6. 为什么事务里不能用 `_.inc()`？

`_.inc()` 是云数据库的**原子自增更新指令**，它的语义是「在服务端把字段值加 n」。
在普通（非事务）更新里它非常好用，能避免读改写竞争。

但在 `db.runTransaction` 里我刻意不用它，原因是：

**第一，事务内需要「判断」和「写」基于同一份快照。** 事务的核心目的是
「读到的值 → 判断 → 写回」这三步不可分割。如果我用 `_.inc(-amount)`，
那么写回的表达式与我在 JS 里读到的值是**两个独立的东西** ——
校验时用的是 `txBuyer.coins`，写入时用的是服务端的当前值，两者可能不是同一个快照。
一旦它们脱钩，校验就失去了意义。

**第二，绝对值写法让结果可预测、可复现、易调试。** `coins` 计算出来是多少就写多少，
云函数日志里打出来的 `coins` 就是落库的值；出问题时可以直接通过日志复现。
如果用增量指令，实际结果取决于服务端当时的值，日志无法完整还原。

**第三，便于把多个字段的一致性放在一起推理。** 结算时我需要同时保证
`buyer.frozenCoins = b.frozenCoins - amount` 和
`seller.coins = s.coins + amount`，两边用同一份快照读出来的 `amount` 计算，
才能论证「总额守恒」。混用增量指令会破坏这个论证。

> **一句话总结**：`_.inc()` 适合**无并发校验需求的计数场景**（例如技能浏览量 `viewCount`），
> 而事务内的**余额类字段**必须用「读出来 → 算绝对值 → 写绝对值」，才能保证校验与写入基于同一份快照。
> 项目里 `skill.detail` 的浏览量自增就用了 `_.inc(1)`，因为它不需要任何校验。

### Q7. 信用分算法怎么设计的？为什么用时间衰减加权？

**基础规则**：初始 100 分，区间限幅在 `[0, 150]`。
加分项：订单顺利完成双方各 +2、收到 5 星 +1、连续 5 单按时完成 +3；
减分项：收到 4/3/2/1 星分别为 0/−1/−2/−3、接单后取消或爽约 −5、被举报核实成立 −10。

**为什么这些权重要这样取？**（逐条说理由）

| 规则 | 分值 | 设计理由 |
|---|---|---|
| 订单完成 +2 | 小正分 | 这是**最高频**的事件。分值必须小，否则靠刷单就能快速刷满信用分（每次 +2，还需要约 25 单才能从 100 到 150，配合分级限制能有效拖慢） |
| 5 星 +1 / 4 星 0 | 微正分 | 好评是「应该的」，不该给太多奖励；4 星视为「正常完成」，不加不减 |
| 3 星 −1 / 2 星 −2 / 1 星 −3 | 递增惩罚 | **差的越狠罚得越多**，且 1 星要明显重于 3 星。这样「偶尔一次一般评价」不会伤筋动骨，但「明显差评」有真实代价 |
| 爽约 −5 | 重罚 | 爽约是**对他人的时间造成实际损害**的行为（对方白等一场），比一次差评严重得多。−5 相当于抵消 2.5 次成功订单 |
| 举报成立 −10 | 最重罚 | 这是唯一需要管理员人工介入判定的规则，代表**违反平台底线**（诈骗、骚扰、违规内容），必须一次就打疼 |
| 连续 5 单按时 +3 | 行为激励 | 奖励「长期稳定守时」而非「单次表现好」。用 `ontimeStreak` 计数器追踪，一次爽约归零 |

**时间衰减加权的公式**（用于展示「综合评分」，不是信用分本身）：

$$w_i = 0.9^{\,\Delta t_i / 24}, \qquad \Delta t_i = \text{距今小时数}$$

$$\text{综合评分} = \frac{\sum_{i=1}^{n} \text{score}_i \cdot w_i}{\sum_{i=1}^{n} w_i}$$

**为什么用这个形式？** 三个理由：

1. **半衰期明确、可解释**。`0.9` 这个底数意味着：**评价每过 24 小时，权重变为原来的 90%**。
   过 7 天权重约 47%，过 30 天约 4%。答辩时可以直接说「约 6.6 天权重减半」
   （$0.9^x = 0.5 \Rightarrow x \approx 6.58$ 天），是个很好解释的数。
2. **它是对「近期表现」的强调，而不是丢弃历史**。如果用「只统计最近 10 条」这种窗口法，
   历史口碑会被硬切断；指数衰减是平滑的，老评价仍然有贡献，只是越来越小。
   对校园场景很合适 —— 一个大二时口碑很好的同学，大三换了方向，新评价应该更快地反映他的现状。
3. **计算量极小**。`Math.pow(0.9, days)` 一次幂运算，前端 `utils/credit.js` 和服务端都可以实时算，
   不需要定期重算任务。项目里 `weightedRating(reviews)` 就是这不到 10 行代码。

**为什么上限是 150？**

1. **防止分数无限膨胀失去区分度**。如果无上限，长期活跃用户的分数会趋向无穷，
   而信用分的用途是**分级授权益**（决定可同时进行几单），一旦所有人都顶到最高等级，
   分级就失效了。
2. **让「从 100 到 150」成为一个有意义的长期目标**。按每次订单 +2 算，
   从 100 到 150 至少需要 25 次成功订单且零差评零爽约，是个有难度但可达成的目标。
3. **让扣分有真实痛感**。上限 150 同时意味着有 50 分的上行空间；
   而一次爽约 −5、一次举报成立 −10，掉到 80 分以下就会从「可同时 3 单」掉到「可同时 2 单」，
   权益损失是可感知的。
4. 下限 0 则意味着「信用分不会为负」，避免出现负分导致的奇怪逻辑（比如负分反而比 0 分更差时的分级判定）。

（如果老师追问「150 是怎么定的，有没有数据支撑」：诚实回答是**经验取值**，
参考了常见信用评级体系的「基准分 + 上行空间」比例，缺少本校真实数据校准。
这已经写进了「不足与改进」里，后续计划是做参数敏感性实验。）

### Q8. 附近技能怎么实现的？为什么不用腾讯位置服务？

**实现方式**（`cloudfunctions/skill/index.js` 的 `actionList`）：

发布技能时前端调 `wx.chooseLocation()` 拿到 `{ latitude, longitude, name, address }`，
云函数把它转成云开发的地理点类型存下来：

```js
location: geo ? db.Geo.Point(geo.lng, geo.lat) : null
```

查「离我最近」时，云函数用地理查询命令：

```js
const near = withCondition(where, {
  location: _.geoNear({
    geometry: db.Geo.Point(geo.lng, geo.lat),
    maxDistance: radius            // 默认 3000 米，可传参覆盖
  })
})
const res = await db.collection(C.SKILLS).where(near)
  .orderBy('location', 'asc')      // geoNear 天然按距离升序
  .skip((page - 1) * size).limit(size).get()

const list = res.data.map(item => Object.assign({}, item, {
  distance: Math.round(Number(item.distance) || 0)   // ★ 结果自带 distance（米）
}))
```

**关键点：`geoNear` 的返回结果自带 `distance` 字段（单位米）**。这意味着
筛选（`maxDistance`）、排序（`orderBy('location')`）、距离计算（`distance`）
三件事**一次数据库查询全部搞定**，不需要任何后处理。

**为什么不用腾讯位置服务？** 因为数据库已经原生提供了这个能力。

| 要做的事 | 云开发原生 | 如果引入腾讯位置服务 |
|---|---|---|
| 按距离筛选 | `_.geoNear({ maxDistance })` | 需要调「周边搜索」接口，或自己拉全量再算 |
| 按距离排序 | `.orderBy('location', 'asc')` | 需要在应用层排序（拿不到数据库排序） |
| 计算距离 | 结果自带 `distance` | 需要自己写 Haversine 公式，或调「距离计算」接口 |
| 申请 Key / 配额管理 | **不需要** | 需要注册、申请 Key、处理 WebService 配额与签名 |
| 网络依赖 | **无**（数据库内网） | 每次都要外网请求第三方，失败要重试 |
| 费用 | 包含在云开发内 | 超出免费配额要付费 |

引入腾讯位置服务只会增加**一个 Key、一层网络依赖、一份配额风险**，
换来的是数据库本来就能给出的距离值 —— 收益为负。

**那项目里为什么还有 `utils/qqmap.js`？** 因为它做的是数据库**做不了**的一件事：
**逆地址解析** —— 把 `(113.93, 22.53)` 这样的坐标翻译成「东区宿舍」这样的中文地点名。
这是纯数据库无法完成的任务，所以保留为**可选增强**：

```js
if (qqmap.available()) {                 // ← 没配 Key 时返回 false
  qqmap.reverseGeocoder(lat, lng).then(r => { ... })
}
```

`app.js` 里先判断 `qqmap.available()`，没有 Key 就跳过，`locationName` 保持空字符串，
页面显示降级为「校园内」。**所有功能都正常** —— 附近排序、距离计算、地图选点
一个都不受影响。所以可以说：**本项目零第三方 SDK 依赖**。

> ⚠️ 部署时别忘了：`skills.location` **必须建地理索引**，否则 `geoNear` 查询会直接报错
> 「no geo index」。这是最容易漏的一条配置（见 [部署指南 报错 #5](部署指南.md#12-常见报错排查表)）。

### Q9. 实时聊天怎么实现？watch 断线怎么办？消息安全怎么保证？

**实现方式**（`Campus Time Bank/pages/chat/room/room.js` 的 `_startRealtime()`）：

```js
this.watcher = db.collection('messages')
  .where({ chatId: chatId })
  .orderBy('createTime', 'asc')
  .watch({
    onChange: snapshot => {
      const docs = (snapshot && snapshot.docs) || []
      const list = this._withPending(docs)      // 合并本地乐观插入的消息
      this._raw = list
      this._render(list.slice(-MAX_MESSAGES))   // 只渲染最近 N 条
      this.setData({ realtimeDegraded: false })
    },
    onError: err => {
      // 实时连接失败 → 降级为 3 秒轮询
      if (this.watcher) { this.watcher.close(); this.watcher = null }
      this.setData({ realtimeDegraded: true })
      util.toast('实时连接已断开，已切换轮询')
      this._startPolling(POLL_INTERVAL, false)
    }
  })
```

**`watch` 的原理**：它是云开发提供的一种**长连接实时推送**能力。
客户端第一次建立连接时，服务端会把当前查询结果集全量下发；
之后任何影响这个结果集的写入（增删改），服务端都会主动把**新的全量结果集**推给客户端。
所以 `onChange` 回调里的 `snapshot.docs` 就是**当前完整的结果集**，
可以直接 `setData({ messages: snapshot.docs })`，**不需要自己算增量** ——
这大大简化了前端逻辑（不用做 diff、不用维护本地列表的增删改）。

**断线降级**：`onError` 触发的原因有几种 —— 网络断开、云环境权限变动、
长时间空闲被回收、页面长时间后台。处理策略是：

1. **立刻关闭失效的 watcher**（`watcher.close()`，避免残留连接）；
2. **切换到 3 秒轮询**：`setInterval` 里调 `api.message.history({ chatId, page:1, size: PAGE_SIZE })`，
   拿到列表后渲染。轮询函数每次都检查 `this._destroyed`，页面已销毁就直接退出，
   避免在卸载的页面上 `setData` 报错；
3. **明确提示用户**：`util.toast('实时连接已断开，已切换轮询')` ——
   不能让用户以为消息不来了，也不能假装还是实时的；
4. **轮询失败静默**：单次轮询失败不弹错（否则弱网下会连续弹 toast），下一次 tick 继续尝试。

另外在**离线预览模式（MOCK）**下不走 `watch`（没有云环境必然失败），
直接启用 2 秒轮询并设置 `mockMode: true`，这样答辩彩排时消息也能「动起来」。

**连接泄漏防护**（这是 `watch` 最容易出的 bug）：

```js
onUnload() {
  this._destroyed = true
  this._stopRealtime()      // 内部：watcher.close() + clearInterval(pollTimer)
  ...
}
```

`watch` 建立的是**长连接**，每个用户开一个聊天室就占一条；
如果不关闭，用户来回进出聊天室十几次就会累积十几条僵尸连接，
轻则消耗配额、重则后续连接建立失败。所以项目把 `watcher.close()` 和
`clearInterval()` 统一收进 `_stopRealtime()`，`onUnload` 和 `onHide` 都会调用。

**消息安全**分三层：

1. **数据库层**：`messages` 集合权限是「所有用户可读，**仅创建者可写**」——
   客户端能建立 `watch`（需要读权限），但**无法直接写入**（没有写权限）。
2. **云函数层**：发消息必须调 `message.send`，服务端会先查 `chats` 文档，
   断言调用者与 `toId` 都出现在 `chats.members` 数组里。不满足直接抛 403。
   这样就防止了「任意用户往别人的会话里塞消息」。
3. **展示层**：聊天室只 `watch` 自己参与的 `chatId`，
   `where({ chatId })` 条件让结果集天然局限于该会话。

**诚实地讲一个不足**：`messages` 开放读权限意味着**理论上**任何用户都可以
构造查询读取全部消息文档。这是为了换取 `watch` 实时能力付出的隐私代价，
也是本项目的一个**已知取舍**。生产环境应该改为「云函数推送 + 客户端轮询自己的 `toId`」
或使用服务端 WebSocket 转发，以彻底关闭 `messages` 的读权限。
这一点我写进了「不足与改进」（见 [核心机制说明 §5.6](核心机制说明.md)）。

### Q10. 为什么选原生小程序，不用 uni-app？

三个理由，按重要性排序：

**第一，本项目只上微信一端，跨端能力毫无价值。** uni-app 的核心卖点是
「一套代码编译到微信、支付宝、H5、App」。但这个项目从需求上就是校园内的微信生态产品，
不可能上 H5（没有微信登录态，时间币体系无从建立），也不可能上其他平台。
引入 uni-app 只是增加了一层抽象，没有任何一端受益。

**第二，核心能力与云开发深度绑定，跨端框架反而要写适配层。**
本项目的技术亮点——`wx.cloud.callFunction`、`db.collection().watch()` 实时长连接、
`cloud.openapi.subscribeMessage` 订阅消息、云函数定时触发器、
`db.Geo.Point` 地理位置查询——全部是**微信云开发独有**的能力。
uni-app 对云开发的支持是「能在里面调 `wx.cloud`」，但 `watch` 这类能力
往往要在条件编译里写平台特有代码，最终代码里到处是 `#ifdef MP-WEIXIN`，
既没有减少工作量，还增加了理解成本。

**第三，零依赖带来真实的工程便利。** 原生开发不需要 `npm install`、
不需要「工具 → 构建 npm」这一步。下载仓库 → 用开发者工具导入 → 直接编译跑起来。
答辩机器上不会出现「`node_modules` 装不上」「构建 npm 失败」的尴尬。
而且页面四件套（`js/json/wxml/wxss`）结构简单，评委老师随便点开一个文件都能读懂，
这对毕设答辩是加分项。

（如果老师问「那如果以后要跨端怎么办」：云函数层是纯 Node.js，完全可复用；
数据模型与业务规则也都在云函数里；只有视图层需要重写。
换句话说，架构上已经把可复用的部分都放在了跨端无关的云函数层。）

### Q11. 数据库为什么做冗余快照？会不会导致不一致？

**为什么做**：云开发数据库**不支持跨集合 JOIN**（只能在同集合内做聚合 `lookup`，
代价高且受 100 条结果集限制）。而广场列表每页 10 条技能，如果不去冗余，
就要为每条技能查一次 `users` 拿作者昵称和信用分 —— **一次列表请求变成 11 次数据库查询**。
在云函数里这既慢又容易触发超时。

所以我在写入时就把关联数据快照下来：
`skills.authorInfo`（作者快照）、`orders.skillSnapshot`（下单时的技能快照）、
`chats.memberInfos`（会话成员快照）、`reviews.fromInfo / toInfo`（评价双方快照）。

**会不会不一致？不会，因为我把快照定义为「历史事实」而不是「当前状态」。**

这是个关键的设计决策，我用两个例子说明：

- **用户改了昵称** → **新发布**的技能用新昵称，**旧**技能和**旧**订单保留旧昵称。
  这不是 bug，是刻意行为。订单是交易凭据，不能因为用户改名就篡改历史记录。
  电商系统的订单快照也是这个逻辑 —— 你半年前买的东西，订单上显示的还是当时的商品名。
- **技能被下架或删除** → 订单里的 `skillSnapshot` 依然完整，
  买家仍然能确认完成、仍然能评价、订单详情仍然显示「当时买的是什么、花了多少钱」。
  如果订单依赖实时查技能表（可能已被删除），订单就废了。

**需要「当前状态」时怎么办？** 直接查 `users`。详情页就是这么做的 ——
`skill.detail` 同时返回 **`skill`（含快照）+ `author`（实时用户文档）** 两个字段：
卡片列表用快照（省查询），详情页用实时数据（保证最新）。
前端根据场景选用哪一个。

**冗余带来的维护成本**是可控的：快照字段只在**写入时**生成一次，之后不再更新。
所以不存在「快照与源数据不一致需要同步」的问题 —— 它本来就是一份凝固的历史副本。
需要同步的只有 `skills.orderCount` 这类**统计型冗余**，
而它们全部在事务内与业务操作一起更新（下单时 `orderCount + 1`）。

### Q12. 定时任务失败怎么办？

**答：有「双保险」，定时任务漏跑不会造成资金问题。**

设计动机：云开发的定时触发器**不保证准时**——
存在触发抖动（高峰期延迟）、函数冷启动延迟，而且如果在触发器触发的时间点
恰好正在发布新版本，还可能**错过这一次触发**。如果只靠定时任务，
用户就可能在这段空窗里看到一条早已过期却还显示「待接单」的订单，
买家的时间币被无限期冻着。

所以超时处理做了两层（`cloudfunctions/order/index.js`）：

**第一层：定时触发器（主路径）**
`cloudfunctions/order/config.json` 配了每 10 分钟执行一次的触发器：
```json
"triggers": [{ "name": "orderAutoTask", "type": "timer", "config": "0 */10 * * * * *" }]
```
入口处识别定时事件（定时触发时 `event` 形如 `{ Type: 'Timer', TriggerName: 'orderAutoTask' }`，
**没有 OPENID**，所以这条分支刻意不做登录校验）：
```js
if (event.action === 'autoTask' || event.Type === 'Timer') {
  return actionAutoTask()      // 批量扫全库的超时订单，不依赖任何用户在线
}
```
它处理两类超时：`status='waiting'` 且 `expireTime < now` → 自动关闭并解冻退款；
`status='confirming'` 且 `finishTime + 72h < now` → 自动结算给服务者。
单批上限 50 条（`batch: 50`）防止云函数超时。

**第二层：惰性检查（兜底）**
任意用户调 `order.counts` 时顺手做一次检查：
```js
async function actionCounts(event, openid) {
  await requireUser(openid)
  await handleTimeouts({ batch: 20 })    // ← 顺手清一遍超时单
  // ...再统计各状态数量
}
```
用户打开「订单」页（tabBar 第 2 项）就会触发，所以**只要有人用小程序，超时单就会被清理**。

**两层互补的关系**：
- 定时任务兜住「**没人访问**」的订单 —— 如果全校没人打开小程序，惰性检查就不会触发；
- 惰性检查兜住「**定时任务没跑或跑晚了**」的窗口 —— 用户一访问就立刻修正。

**为什么重复执行是安全的？** 两条路径都调用同一组内部函数
（`closeAndRefund()` / `settleOrder()`），而这两个函数内部都有**状态断言**：

```js
assert(CANCELABLE_STATUS.indexOf(o.status) > -1, '当前状态不能取消或关闭', 409)  // closeAndRefund
assert(txOrder.status === 'confirming', '当前状态不能确认', 409)                // settleOrder
```

所以第二次执行会因为状态不符直接抛异常退出，**幂等**，不会重复退款或重复结算。
外层还有 `try/catch` 逐条捕获，一条订单处理失败不影响其他订单。

### Q13. 项目难点是什么？

我认为有三个真实的难点，按解决难度排序：

**难点一：设计一个「账实永远对得上」的记账系统。**
一开始我的想法很简单 —— 下单就把钱从买家扣掉、给卖家加上。
但写到「取消订单」时就发现崩了：钱已经打给别人，取消时怎么办？
让卖家退回来？如果卖家不配合呢？这才意识到**必须先冻结、后结算**。
确定了两阶段之后，还有一系列连锁问题：冻结额放在哪个字段？
事务里该不该用 `_.inc()`？流水和余额谁先写？
流水写失败了要不要回滚整个订单？最终形成的方案是：
**「余额只改绝对值、流水一律事务外 bestEffort 补写、任何时刻总量守恒」**，
这三条规则一起构成了一个可以证明正确的记账模型。

**难点二：实时聊天的权限模型。**
`watch` 需要客户端有读权限，但一旦开放读权限，隐私就有风险；
而如果为了安全把权限设成「仅管理端可读写」，`watch` 直接建立不起来。
我得在「功能可用」和「数据安全」之间找平衡点 ——
最终方案是「开放读 + 写入强制走云函数 + 服务端校验会话成员」，
并把残余风险如实写进「不足与改进」。这个过程让我理解了：
**工程里很多问题没有完美解，只有可解释的取舍。**

**难点三：云开发的工程化约束。**
云开发的几个限制在第一版代码里都让我踩了坑：
① 每个云函数**独立打包**，不能跨目录 `require('../_shared')` ——
   逼我想出「单一源码 + 构建同步」的方案（`tools/sync-shared.mjs`）；
② 云函数单次 `get()` 最多返回 **100 条**，聚合 `group` 结果集也最多 100 条 ——
   导致管理端统计会「静默截断」，统计数据偏小。
   解决办法是写 `fetchAll()`（循环 `skip`/`limit` 取全量）和
   `groupCount()`（按 100 条翻页取全部分组），并用 `GET_MAX`/`cap` 做保护上限；
③ 定时触发器不精确 —— 逼出了「双保险」设计。
这三个坑最终都变成了项目里的工程亮点（也都写进了文档）。

### Q14. 有什么不足和改进方向？

我总结了五点不足，都尽量说得具体：

| # | 不足 | 影响 | 改进方向 |
|---|---|---|---|
| 1 | **`messages` 集合开放了读权限** | 为保证 `watch` 实时能力，理论上其他用户能读到不属于自己的消息 | 改为「云函数推送 + 客户端轮询自己的 `toId`」，或服务端 WebSocket 转发；彻底关闭 `messages` 的读权限。代价是失去云开发原生的实时能力，需要自建长连接服务 |
| 2 | **信用分规则权重是经验取值** | `+2 / +1 / −5 / −10` 这些数字没有真实数据校准，可能过严或过松 | 收集一定量真实数据后做参数敏感性实验；把规则做成 `config` 集合里的可配置项，支持按学校特点调参 |
| 3 | **自动化测试有明确的能力边界** | 测试跑在内存版 `wx-server-sdk` 上，**不连接真实云环境**，因此云开发特有的能力（`geoNear` 地理索引、聚合管道 `$`、`watch` 长连接推送、真实 `openapi.subscribeMessage` 返回码、单次 `get` 的 1000 条上限、冷启动与并发压测）都不在覆盖范围内 | ① 补齐端到端测试：用云开发测试环境跑一遍真实链路；② 对 `geoNear` 这类无法在内存里模拟的查询，做「部署后人工回归清单」；③ 把压测单独做成脚本，观察真实冷启动与并发表现 |
| 4 | **认证流程依赖人工审核** | 管理员工作量随用户增长线性增加，也是伪造学生证的薄弱环节 | 接入校园统一身份认证（CAS / 教务系统对接）做自动校验；或至少引入「学号 + 学校邮箱」双重验证 |
| 5 | **技能匹配无推荐算法** | 广场是按时间/热度/距离排序，用户需要自己筛选 | 基于用户标签、历史订单分类、协同过滤做个性化推荐；也可以先用简单规则（同学院优先、互补技能优先） |

**还可以补充的长期方向**：
- **时间币跨校互通**：目前是单校闭环，多校需要解决信任与结算问题；
- **服务过程留痕**：目前靠双方确认，可以引入签到码、服务时长自动计量；
- **数据可视化升级**：管理端可以增加地理热力图（哪些区域需求最密集）、
  用户留存漏斗等更深入的分析。

### Q15. 云开发和其他后端方案（如自建服务器）比有什么优劣？

**优势**（也是我选它的原因）：
1. **零运维**：不用买服务器、不用配域名与 HTTPS 证书、不用管数据库备份与扩容。
   对一个本科毕设来说，把时间花在业务逻辑上比花在运维上更有价值。
2. **天然鉴权**：`cloud.getWXContext().OPENID` 直接拿到可信的用户标识，
   不需要自己做登录态、token、session（这也是为什么能用 `_openid` 当业务主键）。
3. **与小程序权限模型打通**：集合权限可以按 `_openid` 自动判定，
   客户端直连数据库的能力（`watch`）是自建后端很难低成本实现的。
4. **免费额度够用**：按估算，一所学院一学期的数据量约 230 MB，
   占免费额度 2 GB 的约 12%。

**劣势**（也要如实说）：
1. **被平台锁定**：业务逻辑与 `wx-server-sdk` 深度绑定，
   迁移到其他平台需要重写云函数层。
2. **事务能力弱于专业数据库**：云开发事务有时长限制，
   参与文档越多越容易超时，所以我把流水和通知都放到事务外。
   专业数据库可以用更细粒度的锁或更成熟的事务隔离级别。
3. **单次查询 100 条上限**：被迫在统计场景写分页拉全量的代码。
4. **实时能力 = 权限开放**：`watch` 与最小权限原则存在张力（见 Q14 第 1 条）。

**结论**：对「校园规模 + 单端小程序 + 毕设周期」这三个约束来说，
云开发的收益远大于代价。如果是商业产品，我会考虑「云函数只做网关，
核心业务放到自建服务 + 专业数据库」。

### Q16. 你怎么保证代码质量？做过哪些测试？

四层保障，其中两层是**可以现场演示的自动化测试**：

**第一层：云函数业务规则回归（最有说服力）。** `node tools/test-cloudfunctions/run.js` ——
一套**纯 Node、零依赖、不连云环境**的测试，用自研的内存版 `wx-server-sdk`（含事务的快照隔离、
写冲突检测与自动重试语义）把 `order`（时间币事务核心）与 `wallet` 的全部业务规则跑一遍：

- **规模：88 组 / 1901 条断言 / 121 次数据库事务（其中 7 次写冲突自动重试），约 1 秒跑完**，退出码 0/1 可直接接 CI。
- **最能说明问题的三组**：
  - **组 3 · 并发防超卖**：4 个并发下单只成功 3 单；`coins + frozenCoins` 恒为 10；订单金额之和 = 买家冻结额；技能 `orderCount` 不丢计数；**事务冲突重试次数 > 0**（这是「冲突检测真的被触发过」的硬证据）。
  - **组 7 · finish → confirm 结算**：确认前「钱锁在买家名下、卖家余额为 0」；确认后冻结清零、卖家到账、双方 +2 信用分、`totalEarned/totalSpent` 与 `serveCount/buyCount` 同步累加；**`coins + frozen` 总量守恒**；连续 5 单额外 +3；徽章去重补发。
  - **组 10 · autoTask 幂等**：定时触发器无登录态可跑；**重复执行 `closed/settled` 均为 0**，余额、流水、`serveCount` 不重复变化；单批上限 50（60 张超时单分两轮处理完）。
- 测试直接跑仓库里的真源码（劫持 `Module._resolveFilename` 把 `require('./shared')` 指向 `_shared/index.js`），
  所以**实现一改测试立刻跟着变**，不存在「测试副本与实现脱节」。

**第二层：离线数据层冒烟。** `node tools/smoke-test-mock.js` 会自动扫描
`utils/api.js` 里声明的**全部 65 个 action**（用正则从源码里提取 `call('ns','action')`），
在 Node 环境里逐个真实调用一遍，并断言订单状态机的关键行为：

- 拒单后买家时间币是否真的退回（比对退款前后的 `coins`）；
- `waiting` 阶段取消**不应该**扣信用分；
- 确认完成后卖家 `coins` 是否 `+1`、信用分是否 `+2`；
- 评价后 `isRatedBuyer` 是否被写入；
- 发消息后 `messages` 是否真的多了一条。

当前结果：**通过 65 失败 0 跳过 0，覆盖率 65/65**。

**第三层：结构一致性自检。** `node tools/check-project.mjs`（当前**全部检查通过**）覆盖：
页面四件套完整性、`usingComponents` 路径可解析（**69 处组件引用**）、
页面调用的 `api.xxx.yyy()` 是否都存在、`api.js` 的每个 action 是否有 mock 实现（65/65）、
相对路径 `require()` 是否可解析（**131 处**）、tabBar 声明与 `pages` 一致、
云函数目录结构完整、事件绑定的处理函数是否存在（**228 个**）、
`wx:for` 使用（**81 处**）、模板变量引用（**438 个**）、`app.*` 调用（**26 处**）。
其中最实用的是「调了不存在的接口」和「加了接口忘了写 mock」这两项 ——
它们都是离线开发时最容易出现、人工又很难查的问题。

**第四层：人工功能测试。** `docs/测试用例.md` 里按 10 个模块写了 50+ 条测试用例，
每条都具体到可操作（例如「余额 1 时间币时购买 2 时间币的服务 →
提示『时间币不足，还差 1 枚』，下单按钮置灰」），
并有专门的「边界与异常测试要点」清单（并发下单、余额恰好等于价格、
订单重复评价、非参与方访问订单详情等）。

**测试边界（如实说明）**：上面两层自动化测试用的是**内存 stub**，
不连接真实云环境，因此**不覆盖云开发的网络与权限层** ——
`geoNear` 地理索引、聚合管道 `$`、`watch` 长连接推送、真实
`openapi.subscribeMessage` 返回码、单次 `get` 的 1000 条上限、冷启动与并发压测
都不在覆盖范围内。测试台自己的 `README.md` 里有一节「暂时没有覆盖的部分」
专门写这些。**我认为说清测试边界比宣称「全覆盖」更经得起追问。**

**另外，离线模式本身就是一种质量保障手段**：所有页面的业务逻辑都能在没有云环境的情况下
跑起来，意味着 UI 层与数据层的解耦是彻底的 —— 而这只有在接口契约
（`ARCHITECTURE.md`）被严格遵守时才可能做到。

### Q17. 时间币的经济系统会不会通胀？

**短期内不会，长期需要治理。** 分析一下：

**增发入口只有两个**：注册赠送（默认 5 枚）和管理员仲裁调整。
**消耗出口只有两个**：买家确认完成后的结算支出、管理员调整。

关键在于：**「服务收入」与「买家支出」是同一笔金额的转移**，
订单流转过程中平台总量不变。所以真正会推高总量的只有新用户注册
和 管理员调整。

**通胀风险来自哪里？** 如果新用户持续涌入，人均持有量会上升；
如果老用户的时间币只赚不花（囤币），流通性会下降。
本项目用三个机制缓解：

1. **注册赠送只有一次**，且有 `isNew` 判断保证幂等，不能靠反复注册刷币
   （同一 openid 只有一条 `users` 文档，登录逻辑是「查不到才建」）。
2. **管理员看板暴露总量指标**：`coinCirculation`（流通量）、`coinFrozen`（冻结量）、
   `coinEarned`（累计产生）。管理员可以随时观察「流通量 / 活跃用户数」的趋势，
   如果发现异常膨胀，可以用 `admin.adjustCoins` 做定向回收。
3. **`config.serviceFee` 预留了手续费参数**（当前为 0，即不抽成）。
   如果未来需要回收流动性，把它设成非零值，结算时抽取一部分销毁即可 ——
   字段和读取逻辑都已经在 `getConfig()` 里，不需要改代码结构。

**一个诚实的局限**：目前没有做「时间币自动销毁机制」，
也没有做通胀率的自动监控与告警，而是依赖管理员主动观察看板。
更完善的方案是引入「时间币有效期」（如每学期末按比例回收），
但这会给用户体验带来较大影响，需要谨慎评估。

### Q18. 你们的数据隐私怎么保护？

分几个层面：

**第一，最小权限原则。** 14 个集合中 12 个是「仅管理端可读写」，
客户端**完全无法直连**，所有读写都必须过云函数，云函数里做身份与状态校验
（`requireUser` / `requireVerified` / `requireAdmin` 三道关卡）。

**第二，敏感字段过滤。** 对外返回用户信息时统一走 `_shared` 的 `publicUser(u)`，
它用一个黑名单常量删掉五个字段：

```js
const PUBLIC_USER_BLACKLIST = ['phone', 'studentNo', 'realName', 'authImages', 'authRemark']

function publicUser(u) {
  if (!u) return null
  const o = Object.assign({}, u)
  PUBLIC_USER_BLACKLIST.forEach(k => { delete o[k] })
  return o
}
```

所以即使调 `login.getUser` 看别人主页，也拿不到手机号、学号和认证照片。

**第三，订单可见性控制。** `order.detail` 断言调用者必须是买家或卖家，
非参与方（包括其他普通用户）访问会抛 403；管理员例外（用于纠纷仲裁）。

**第四，举报的匿名保护。** `reports` 集合是「仅管理端可读写」，
举报人信息不会暴露给被举报人。

**第五，小程序隐私合规。** `app.json` 里声明了
`permission.scope.userLocation` 的用途说明（「用于为你展示附近的技能服务，
以及发布时在地图上选择服务地点」）和 `requiredPrivateInfos: ["getLocation", "chooseLocation"]`；
上线前还需要在公众平台补充《用户隐私保护指引》，声明收集的类型（位置、相册、手机号）。

**已知的隐私风险（如实说明）**：`messages` 集合为保证 `watch` 实时聊天开放了读权限，
理论上其他用户能构造查询读取全部消息文档。这是本项目最主要的一处隐私妥协，
改进方向见 Q14 第 1 条。**我认为把这个问题主动讲出来，比被老师问出来要好。**

### Q20. 用户不确认完成怎么办？会不会一直冻结着？

**不会。设计了两条自动结算路径。**

**路径一：72 小时超时自动确认（针对「待确认」状态）**

服务流程走到 `confirming`（卖家已标记完成，等待买家确认）后，
如果买家一直不确认，超过 `config.confirmExpireHours`（默认 **72 小时**），
定时触发器会自动结算给服务者：

```js
const threshold = new Date(Date.now() - confirmHours * 3600000)
const res = await db.collection(C.ORDERS)
  .where({ status: 'confirming', finishTime: _.lt(threshold) })
  .limit(batch).get()
for (const od of (res.data || [])) {
  await settleOrder(od._id, { auto: true, operator: 'system' })
}
```

注意 `settleOrder(orderId, { auto: true })` 与买家手动确认**走的是同一个函数**：

```js
async function settleOrder(orderId, opt) {
  const auto = !!o.auto
  ...
  if (!auto) assert(order0.buyerId === o.operator, '只有买家可以确认完成', 403)
  // auto 模式下跳过「必须是买家」的校验，但状态断言依然保留
  const actor = auto ? 'system' : order0.buyerId
```

时间轴里会记录 `remark: '买家超时未确认，系统自动结算给服务者'`，
`operator: 'system'`，用户查看订单详情时能看到是系统代确认的。

**路径二：24 小时未接单自动关闭（针对「待接单」状态）**

如果卖家一直不接单，超过 `config.orderExpireHours`（默认 **24 小时**）
系统自动关闭订单并**解冻退回**买家时间币：

```js
const res = await db.collection(C.ORDERS)
  .where({ status: 'waiting', expireTime: _.lt(t) })
  .limit(batch).get()
for (const od of (res.data || [])) {
  await closeAndRefund(od, 'system', 'closed', '超时未接单，系统自动取消', ...)
}
```

**为什么两条路径的时间不同（24h vs 72h）？** 因为性质不同：
「没人接单」是**服务没有发生**，应该尽快把钱还给买家让他去找别人；
「待确认」是**服务大概率已经发生了**（卖家主动标记了完成），
所以要给买家足够的时间去核实（可能他这两天没上线），
72 小时是比较宽松但不会让卖家等太久的折中。

**还有一个兜底**：即使定时触发器完全失效，
任意用户调 `order.counts`（打开订单页就会触发）时的惰性检查也会清理超时单。

**最后，买家也可以主动结束冻结吗？** 可以。
在 `waiting` 或 `ongoing` 状态下买家都能取消订单（`order.cancel`），
时间币立即解冻退回。但在 `ongoing` 阶段取消属于「已接单后取消 / 爽约」，
买家会被扣 5 分信用分并清零连续按时完成记录 —— 这是对服务者时间的补偿性约束。

### Q21. 管理员能做什么？会不会滥用权限？

**管理员的能力**（`admin` 云函数的 20 个 action）：

| 类别 | 能力 | 是否留痕 |
|---|---|---|
| 数据看板 | 用户/订单/时间币/评分统计、7 类图表 | — |
| 用户管理 | 搜索、封禁/解封、设为管理员、**调整时间币** | 调整时间币会写 `admin` 类型流水 ✅ |
| 认证审核 | 通过 / 驳回校园认证（会发通知） | 写 `notices` ✅ |
| 技能审核 | 上架 / 违规下架 | 写 `skills.auditRemark` ✅ |
| 分类管理 | 增删改、排序（有技能引用时拒绝删除） | — |
| 订单管理 | 查看全部订单（参与方之外的唯一可查看者） | — |
| 举报处理 | 处理 / 驳回，并据此扣信用分 | 写 `reports.handleRemark` + `handlerId` + `handleTime`；扣分写 `credit_logs` ✅ |
| 轮播与配置 | 维护首页轮播、全局参数 | — |

**防滥用设计**：

1. **所有 admin action 都过 `requireAdmin()`** —— 除 `check` 外每一个 action
   开头都有 `await requireAdmin()`，它会断言 `role === 'admin'`，
   否则抛 403。（这也是为什么客户端拿到 admin 接口也调不动。）
2. **关键操作留痕**：调整时间币写流水（可追溯到「谁在什么时候给谁调了多少、原因是什么」）；
   举报处理记录处理人、时间、说明；认证审核与举报结果都会写 `notices` 通知当事人。
3. **举报处理与信用分挂钩但可追溯**：判定成立时会扣被举报人 10 分，
   同时在 `credit_logs` 里记录 `reason: 'report_valid'` 与处理人信息，
   如果误判可以管理员手动调回并把过程留在流水里。
4. **删除有引用保护**：`deleteCategory` 在有技能引用时会拒绝执行，
   而不是级联删掉一批技能。

**诚实的局限**：目前没有做「管理员操作审计日志」这样一个独立集合，
留痕分散在各个业务集合里；也没有做「多管理员权限分级」
（比如审核员不能改钱）。改进方向是把管理员操作统一写到一个 `admin_logs` 集合，
并按职责做角色细分。

### Q22. 如果让你重做，你会怎么改？

（这题考的是反思能力，答得越具体越好。）

**架构层面改两件：**

1. **消息系统不用 `watch`，改成服务端推送 + 客户端按需拉取。**
   我会把 `messages` 权限设为「仅管理端可读写」，然后：
   云函数负责写入，客户端用一个带 `toId` 条件的轮询接口（或 `wx.cloud.callFunction` 长轮询）
   只拉自己的消息。代价是实时性从「毫秒级推送」降到「秒级轮询」，
   但换来的是**彻底关闭消息集合的读权限**，消除 Q14 里那条最大的隐私风险。
   如果一定要保留推送，就应该自建 WebSocket 服务，付出运维成本换取安全。

2. **把统计从「云函数内分页拉全量」改成「预聚合 + 增量维护」。**
   现在管理端看板的统计是在云函数里循环 `skip`/`limit` 拉数据再算，
   数据量大了会很慢（`GET_MAX = 3000` 的硬上限也意味着会偏小）。
   更好的做法是维护一张 `stats_daily` 集合，在业务写入时顺手累加当天计数，
   看板只读这张表 —— 用「写放大」换「读极快」。

**业务层面改两件：**

3. **接入校园统一身份认证，取消人工审核。**
   现在认证要靠管理员看学生证照片，既慢又不可靠。
   对接教务系统的 CAS 或至少用「学号 + 学校邮箱验证」能实现自动通过，
   把管理员从重复劳动里解放出来，同时大幅提高伪造门槛。

4. **信用分规则做成可配置 + 加数据校准。**
   把 9 条规则的分值和那 5 个等级区间都挪到 `config` 集合里
   （`getConfig()` 的默认值兜底机制已经支持这种扩展），
   然后收集一个学期的真实评价数据，用「预测爽约概率」为目标做参数拟合，
   而不是拍脑袋取 `−5 / −10`。

**工程层面改一件：**

5. **把 `check-project.mjs` 接进 CI。**
   现在它是手动跑的。如果放到 Git 提交钩子或 GitHub Actions 里，
   每次提交自动跑静态体检 + 冒烟测试，就能保证「共享层改了没同步」
   「加了接口忘了写 mock」这类问题在提交时就被拦住，
   而不是等到部署后发现云函数报错。

**最后一点感受**：如果重做，我会**先写接口契约再写代码**。
这次能顺利推进，很大程度上是因为一开始就固化了 `ARCHITECTURE.md`
（字段名、action 名、返回结构全部冻结），前后端才没有反复对不上。
这个经验我认为比具体的技术选择更重要。
